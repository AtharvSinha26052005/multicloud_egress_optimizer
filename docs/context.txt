P1  ·  Budget-Constrained Pre-Warming to Reduce Cold-Start Latency in Serverless Platforms
BACKGROUND
In the Function-as-a-Service model, a function that has not been invoked recently is evicted from memory. The next invocation must then wait while the platform allocates a sandbox, loads the runtime and initialises the user code. This delay, known as the cold start, can range from a few hundred milliseconds to several seconds and dominates the response time of infrequently used functions. Commercial platforms mitigate it by keeping recently used functions warm for a fixed period, typically five to ten minutes.
PROBLEM STATEMENT
A fixed keep-alive window treats every function identically. Memory is therefore consumed holding functions that will not be called again, while functions that are about to receive a burst of traffic may already have been evicted. The platform operator has a finite memory budget, so keeping everything warm is not an option. The unsolved question is how to decide which subset of functions to keep warm at any instant, given a memory budget that is smaller than the total memory required to keep all functions resident.
OBJECTIVES
O1.  To characterise the invocation patterns of real serverless workloads and quantify the cold-start penalty incurred under the fixed keep-alive policy.
O2.  To develop a short-horizon prediction model that estimates the probability of each function being invoked in the next few minutes.
O3.  To formulate warm-container selection as a resource-constrained optimisation problem in which the predicted benefit of keeping a function warm is weighed against its memory footprint.
O4.  To implement the resulting policy on a working serverless platform and evaluate the latency improvement obtained per unit of memory spent.
SCOPE OF WORK
1.  Deploy OpenFaaS or Knative on a single-node k3s cluster on a laptop or free-tier VM.
2.  Replay a subset of the Azure Functions invocation trace against the deployment to establish the cold-start latency distribution under the default policy.
3.  Train a per-function invocation predictor using recency, inter-arrival statistics and time-of-day features.
4.  Implement the pre-warming controller, which at each interval selects functions to keep warm by solving a knapsack instance over predicted benefit and memory size.
5.  Repeat the evaluation across at least four memory-budget settings.
BASELINE FOR COMPARISON
The fixed ten-minute keep-alive policy, which is the default behaviour of AWS Lambda and of OpenFaaS, together with a no-warming (always-cold) configuration that establishes the worst case.
EVALUATION METRICS
Median, 95th and 99th percentile cold-start latency; number of cold starts avoided; memory-minutes consumed by warm containers; prediction precision and recall. The principal result is the curve relating latency improvement to memory budget, not any single latency figure.
DATASETS AND TOOLS
Azure Functions Trace 2019 or 2021 (public), k3s, OpenFaaS or Knative, Python with scikit-learn, Locust or a custom replayer.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
The published literature on cold starts concentrates on improving prediction accuracy and assumes memory is available for whatever the predictor recommends. Treating pre-warming as a knapsack problem under an explicit memory budget, and reporting the resulting benefit-versus-budget curve, is the contribution. The paper remains valid even if the predictor is only moderately accurate, because the finding concerns the allocation policy rather than the predictor.
P2  ·  Energy and Performance Characterisation of Four Isolation Technologies for Edge Inference
BACKGROUND
Workloads at the network edge can be isolated in several ways: a full virtual machine under a hypervisor such as KVM, an operating-system container under Docker, a sandboxed container under gVisor, or a lightweight virtual machine under Firecracker. Each represents a different point on the spectrum between strong isolation and low overhead. Published comparisons focus almost entirely on startup latency and throughput.
PROBLEM STATEMENT
Edge deployments are frequently power-constrained, being sited in cabinets, on poles or on battery backup. The energy cost of the isolation layer is therefore a first-order concern, yet it is not reported in the comparative literature. It is not currently possible to answer, from published data, how many joules are consumed per inference under each isolation technology at equal throughput, nor whether the isolation layer that is cheapest in latency is also the cheapest in energy.
OBJECTIVES
O1.  To construct a measurement harness that records energy consumption and latency for an identical inference workload across four isolation technologies.
O2.  To quantify the energy consumed per inference under each technology at matched throughput levels.
O3.  To determine whether the ranking of technologies by energy differs from their ranking by latency, and if so, to identify the cause.
O4.  To produce a reproducible characterisation that practitioners can use to select an isolation technology under a stated power budget.
SCOPE OF WORK
1.  Select a fixed inference workload, for example a quantised MobileNet or a small transformer model, and containerise it once.
2.  Execute the identical workload under bare metal, KVM, Docker, gVisor and Firecracker.
3.  Instrument energy consumption using Intel RAPL through the powercap interface or the perf tool, with a wall-plug meter as an optional cross-check.
4.  Sweep the request arrival rate from light to saturation, holding the model and batch size constant.
5.  Repeat each configuration at least five times and report variance.
BASELINE FOR COMPARISON
Bare-metal execution of the same workload, which establishes the zero-isolation reference against which every overhead figure is expressed.
EVALUATION METRICS
Joules per inference; average power draw in watts; 99th percentile latency at matched throughput; memory resident set size; container or virtual machine startup time.
DATASETS AND TOOLS
KVM/QEMU, Docker, gVisor, Firecracker, powercap or perf for RAPL access, ONNX Runtime or TensorFlow Lite.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
A rigorously measured energy-per-inference table spanning four isolation levels does not currently exist in the literature in a form that can be cited. Characterisation papers of this kind are accepted at sustainable-computing and edge-computing tracks provided the methodology is sound and the variance is reported honestly. The result is publishable regardless of which technology wins.
P3  ·  Workload-Aware Selection Between Pre-Copy and Post-Copy Live Migration of Virtual Machines
BACKGROUND
Live migration moves a running virtual machine between physical hosts without stopping it. Two mechanisms exist. Pre-copy transfers memory pages iteratively while the machine continues to run, then briefly pauses it to transfer the remainder. Post-copy pauses the machine first, transfers minimal state, resumes it on the destination and fetches pages on demand. Hypervisors almost universally default to pre-copy.
PROBLEM STATEMENT
Pre-copy converges only if the network transfer rate exceeds the rate at which the guest dirties memory pages. For write-intensive workloads this condition fails, and the migration iterates repeatedly without progress until a forced cut-over produces a long service interruption. Post-copy does not suffer this failure mode but risks degraded performance from remote page faults. No mechanism currently exists in mainstream hypervisors to select between the two based on the observed behaviour of the guest, so operators either accept the default or choose manually by intuition.
OBJECTIVES
O1.  To quantify the relationship between guest memory-write intensity and the convergence behaviour of pre-copy migration.
O2.  To identify measurable indicators, available to the hypervisor before migration begins, that predict pre-copy failure.
O3.  To design and implement a decision rule that selects pre-copy, post-copy or a hybrid strategy for a given virtual machine.
O4.  To evaluate the decision rule against the hypervisor default across a range of workload write intensities.
SCOPE OF WORK
1.  Configure a two-node KVM/QEMU testbed with shared or replicated storage; two modest VMs or two laptops are sufficient.
2.  Generate guest workloads of controlled memory-write intensity using a memory stressor such as stress-ng.
3.  Instrument the dirty-page rate through the QEMU migration statistics interface.
4.  Train or hand-derive a classifier mapping dirty-page rate and available bandwidth to a migration strategy.
5.  Execute migrations under both the default and the proposed policy across the full write-intensity sweep.
BASELINE FOR COMPARISON
QEMU default pre-copy migration with auto-converge enabled, which is what a production deployment would use without intervention.
EVALUATION METRICS
Total migration time; service downtime during cut-over; total pages transferred; number of pre-copy iterations; application-level throughput degradation during migration.
DATASETS AND TOOLS
KVM/QEMU with libvirt, stress-ng, the QEMU migration monitor, Python for analysis.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
The two migration mechanisms are individually well studied; the automated selection between them, validated against a systematic write-intensity sweep with a stated decision boundary, is the novel element. The identification of the exact dirty-page rate at which pre-copy ceases to be the correct choice is a concrete and citable result.
P4  ·  Interference and Fairness Analysis of Fractional GPU Sharing for Multi-Tenant Inference
BACKGROUND
Graphics processing units are expensive and frequently underutilised by a single inference tenant. Several sharing mechanisms exist: time-slicing, in which the scheduler interleaves contexts; the Multi-Process Service, which allows concurrent kernel execution from multiple processes; and application-level sequential batching, in which requests from all tenants are merged. Cloud providers expose these mechanisms with little guidance on their behaviour.
PROBLEM STATEMENT
When multiple tenants share a single accelerator, the performance each observes depends on the behaviour of the others. The extent of this interference, and whether it is distributed fairly, is not documented for the common sharing mechanisms under mixed batch sizes. Consequently an operator cannot determine how many tenants may share a device before the latency guarantee offered to each becomes unachievable, nor which sharing mechanism degrades most gracefully.
OBJECTIVES
O1.  To measure the performance interference experienced by inference tenants sharing a single GPU under three distinct sharing mechanisms.
O2.  To quantify the fairness of the resulting resource allocation using an accepted fairness index.
O3.  To determine the tenant count at which each mechanism ceases to meet a stated latency target.
O4.  To propose an admission-control rule that admits tenants only while the latency target remains satisfiable.
SCOPE OF WORK
1.  Deploy an inference server hosting two to six concurrent tenants on a single consumer GPU; Google Colab or Kaggle free tiers are adequate.
2.  Configure the three sharing mechanisms in turn without altering the workload.
3.  Vary the batch size and arrival rate independently for each tenant to create heterogeneous conditions.
4.  Record per-tenant latency and throughput throughout.
5.  Derive and validate the admission-control rule on a held-out set of tenant mixes.
BASELINE FOR COMPARISON
Exclusive single-tenant allocation of the whole device, which gives the interference-free reference for each tenant.
EVALUATION METRICS
Aggregate throughput; per-tenant 99th percentile latency; Jain's fairness index across tenants; slowdown relative to exclusive execution; the maximum tenant count satisfying the latency target.
DATASETS AND TOOLS
NVIDIA MPS, CUDA time-slicing, Triton Inference Server or a custom server, PyTorch or ONNX Runtime, a single consumer or cloud GPU.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Interference-aware admission control for fractional GPU sharing is discussed conceptually but rarely measured. Establishing the point at which sharing stops paying, expressed as a rule that can be applied by an operator, is a practical and publishable contribution.
P5  ·  Egress-Aware Cost-Optimal Placement of Workloads Across Multiple Public Cloud Providers
BACKGROUND
Organisations increasingly distribute workloads across more than one public cloud provider to avoid lock-in, exploit price differences and satisfy availability requirements. Each provider publishes a large and frequently changing price list covering compute instances, storage and network transfer.
PROBLEM STATEMENT
Selecting the cheapest instance for each component independently does not minimise total cost, because moving data between providers and between regions incurs egress charges that can exceed the compute saving. The placement problem is therefore coupled: the cost of placing one component depends on where the components that communicate with it have been placed. Existing tooling and much of the published work treats placement as a per-component selection and consequently produces solutions that appear cheap but are not.
OBJECTIVES
O1.  To build a unified cost model spanning compute, storage and inter-provider network transfer for at least three public cloud providers using published pricing data.
O2.  To formulate multi-component workload placement as an optimisation problem in which egress cost between communicating components is represented explicitly.
O3.  To solve the formulation exactly for small instances and heuristically for larger ones, and to quantify the optimality gap of the heuristic.
O4.  To measure the total cost penalty incurred by placement approaches that ignore egress.
SCOPE OF WORK
1.  Retrieve pricing from the AWS Price List API, the GCP Cloud Billing Catalog API and the Azure Retail Prices API, all of which are public and free to query.
2.  Define a set of representative multi-component applications, for example a three-tier web application and a data-processing pipeline, with stated inter-component traffic volumes.
3.  Implement the integer linear programming formulation using an open solver such as PuLP with CBC.
4.  Implement a greedy heuristic and a simulated-annealing heuristic for comparison.
5.  Scale the number of components and candidate regions to establish where exact solution becomes infeasible.
BASELINE FOR COMPARISON
Cheapest-per-vCPU greedy selection performed independently per component, and single-provider placement, which together represent current common practice.
EVALUATION METRICS
Total monthly cost; the proportion of cost attributable to egress; optimality gap of the heuristic relative to the exact solution; solver runtime as a function of problem size.
DATASETS AND TOOLS
Public pricing APIs of AWS, GCP and Azure; Python with PuLP or OR-Tools; no paid cloud account is required since only pricing data is consulted.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
The demonstration that egress cost inverts the placement decision, quantified across realistic application topologies, is the contribution. It is a result that practitioners can act upon and that reviewers can verify from public pricing data.
P6  ·  Hazard-Rate-Adaptive Checkpointing for Long-Running Jobs on Interruptible Cloud Instances
BACKGROUND
Cloud providers sell surplus capacity at a substantial discount as spot or preemptible instances, which may be reclaimed at short notice. Long-running jobs on such instances protect themselves by checkpointing state periodically. Checkpointing too often wastes compute on saving state; checkpointing too rarely wastes compute on repeating work after an interruption.
PROBLEM STATEMENT
The standard checkpoint-interval formula, due to Young and refined by Daly, is derived under the assumption that failures follow an exponential distribution with a constant rate. Spot interruptions do not satisfy this assumption: the interruption hazard varies with instance type, availability zone, time of day and market conditions. Applying a constant-rate formula to a time-varying hazard therefore yields an interval that is systematically wrong, but the size and direction of that error have not been established.
OBJECTIVES
O1.  To characterise the interruption hazard of spot capacity as a function of instance type, availability zone and time, using published provider data.
O2.  To determine the extent to which the constant-rate assumption underlying the Daly formula is violated in practice.
O3.  To derive a checkpoint interval that adapts to the estimated instantaneous hazard rate.
O4.  To evaluate the adaptive interval against the fixed Daly interval in terms of effective job completion time and wasted compute.
SCOPE OF WORK
1.  Collect AWS Spot price history and Spot placement scores, or the equivalent GCP preemptible statistics, over several weeks and across several instance families.
2.  Fit a time-varying hazard model to the observed interruption behaviour.
3.  Implement a checkpointing wrapper around a representative long-running job such as model training or a scientific simulation.
4.  Simulate interruptions drawn from the fitted hazard model, since deliberately provoking real interruptions is neither reliable nor economical.
5.  Compare the fixed and adaptive policies across low, moderate and high interruption regimes.
BASELINE FOR COMPARISON
Fixed-interval checkpointing using the Young/Daly optimal interval computed from the mean interruption rate, which is the standard recommendation in the literature.
EVALUATION METRICS
Effective job completion time including all restarts; compute wasted on repeated work; compute spent on checkpointing; total monetary cost; sensitivity of each to the interruption regime.
DATASETS AND TOOLS
AWS Spot price history via the public API or published datasets, Python for hazard modelling and simulation, any checkpointable long-running workload.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
The mismatch between the exponential-failure assumption and observed spot behaviour is widely acknowledged informally but rarely quantified. Measuring the penalty of that assumption and offering a corrected interval is a well-defined and defensible contribution.
P7  ·  Learned Tiering Policies for Cloud Object Storage Evaluated Against the Optimal Offline Policy
BACKGROUND
Cloud object storage is offered in tiers that trade storage price against retrieval price and retrieval latency. Moving an object to a colder tier reduces the monthly storage charge but introduces a cost and delay if the object is subsequently read. Providers offer rule-based lifecycle policies, typically expressed as a fixed number of days since last access, and automatic tiering services whose internal logic is not published.
PROBLEM STATEMENT
Fixed day-count rules cannot distinguish an object that is genuinely finished with from one that is accessed sporadically but predictably. The consequence is either premature demotion, which incurs retrieval charges, or delayed demotion, which incurs storage charges. How much money is left on the table by fixed rules, and how much of that gap a learned policy can close, has not been established against a principled upper bound.
OBJECTIVES
O1.  To replay realistic access traces against a tiered object store and measure the cost incurred by fixed lifecycle rules.
O2.  To compute the cost of the optimal offline policy, which has perfect knowledge of future accesses, as an upper bound on achievable savings.
O3.  To develop a learned tiering policy using access-pattern features available at decision time.
O4.  To express the performance of the learned policy as the fraction of the gap to the optimal policy that it closes.
SCOPE OF WORK
1.  Deploy MinIO locally with simulated hot, warm and cold tiers whose cost and latency parameters follow published cloud pricing.
2.  Replay the MSR Cambridge block traces and the IBM object store traces against the deployment.
3.  Implement the fixed thirty-day and ninety-day lifecycle rules and a least-recently-used policy.
4.  Compute the optimal offline schedule using dynamic programming over the known trace.
5.  Train and evaluate the learned policy using recency, access frequency, object size and inter-access interval features.
BASELINE FOR COMPARISON
Least-recently-used demotion, static thirty-day and ninety-day lifecycle rules, and the optimal offline policy as the upper bound.
EVALUATION METRICS
Total monthly cost; retrieval latency penalty incurred; number of premature demotions; the fraction of the gap between the fixed rule and the optimal policy that is closed.
DATASETS AND TOOLS
MinIO, MSR Cambridge block traces, IBM object store traces, Python with scikit-learn or XGBoost.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Framing the result as a fraction of the achievable gap, rather than as a raw percentage saving, is what distinguishes this from routine applied machine learning. It also makes the paper publishable when the learned policy performs modestly, since a small gap to optimal is itself an informative finding.
P8  ·  Managed Versus Self-Hosted Database Services Under Bursty Load: A Tail-Latency and Cost-of-Ownership Study
BACKGROUND
A team deploying a relational database in the cloud must choose between a managed service such as Amazon RDS or Google Cloud SQL and a self-managed instance running in a container or virtual machine. Managed services carry a price premium justified by reduced administrative effort, automated backup and automated failover.
PROBLEM STATEMENT
Comparisons between the two options are usually conducted at steady state and report average throughput, under which conditions the self-managed option generally appears superior on price. Real workloads, however, are bursty, and the behaviour that matters is how each option responds when load rises sharply and how quickly it recovers afterwards. That behaviour is not documented, and neither is the administrative time cost that would need to be included for a fair comparison.
OBJECTIVES
O1.  To construct a workload with a realistic diurnal shape and superimposed bursts, rather than a constant request rate.
O2.  To measure the tail-latency behaviour and recovery time of managed and self-managed deployments under that workload.
O3.  To record the administrative effort required to configure, secure, back up and recover each deployment.
O4.  To assemble a three-year total cost of ownership model incorporating both infrastructure charges and administrative time, and to identify the conditions under which each option is preferable.
SCOPE OF WORK
1.  Deploy PostgreSQL both on a managed free-tier service and in a container on a comparably sized virtual machine.
2.  Drive both with the same YCSB or sysbench workload shaped to a diurnal pattern with bursts.
3.  Deliberately induce a failure in each deployment and measure recovery.
4.  Log the wall-clock time spent by the team on administrative tasks throughout the project.
5.  Build the cost model with administrative time as an explicit and varied parameter.
BASELINE FOR COMPARISON
The conventional steady-state throughput comparison, reproduced first, so that the divergence introduced by bursty conditions can be shown directly.
EVALUATION METRICS
99th percentile latency during and after bursts; time to return to baseline latency; failure recovery time; data loss on failure; three-year total cost of ownership as a function of the assumed hourly cost of administrative time.
DATASETS AND TOOLS
PostgreSQL, Docker, a managed database free tier, YCSB or sysbench, a spreadsheet or Python cost model.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
A decision-support study of this kind is valued when it makes its assumptions explicit and identifies the crossover conditions. The burst-recovery dimension and the inclusion of administrative time are the elements absent from vendor-published benchmarks.
P9  ·  Comparative Resilience of the OpenStack and Kubernetes Control Planes Under Systematic Fault Injection
BACKGROUND
A private cloud is managed by a control plane that accepts requests, maintains desired state and reconciles the infrastructure against it. OpenStack and Kubernetes are the two dominant open control planes, differing substantially in architecture: OpenStack is a set of services coordinated through a message queue and a relational database, whereas Kubernetes is a set of controllers reconciling against a distributed key-value store.
PROBLEM STATEMENT
The resilience characteristics of these two architectures are described qualitatively in documentation but have not been compared under identical, systematically injected faults. An operator selecting a control plane therefore cannot determine how each behaves when its database slows, when a component is killed, or when the network partitions, nor whether operations that were in flight at the moment of failure are lost, duplicated or correctly completed.
OBJECTIVES
O1.  To define a fault taxonomy covering component failure, storage-layer degradation and network partition that can be applied identically to both control planes.
O2.  To measure the time each control plane requires to detect and recover from each injected fault.
O3.  To determine the fate of operations that were in flight when the fault occurred.
O4.  To identify architectural causes for any observed differences in resilience.
SCOPE OF WORK
1.  Deploy DevStack in an all-in-one configuration and a k3s cluster, each on modest hardware.
2.  Implement the fault-injection taxonomy using process termination, traffic control for latency injection, and firewall rules for partitioning.
3.  Submit a continuous stream of provisioning operations so that faults always occur with work in flight.
4.  Repeat each fault at least five times to capture variance in recovery behaviour.
5.  Classify every in-flight operation as completed, lost, duplicated or left inconsistent.
BASELINE FOR COMPARISON
The recovery behaviour documented or advertised for each platform, against which the measured behaviour is compared; deviations between the two are themselves findings.
EVALUATION METRICS
Time to detect; time to recover; count of lost, duplicated and inconsistent operations; whether manual intervention was required; resource consumption during recovery.
DATASETS AND TOOLS
DevStack, k3s, Linux tc for network fault injection, iptables, a custom operation-submission harness.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Applying a single consistent fault taxonomy to two architecturally distinct control planes produces a comparison that does not presently exist. Chaos-engineering methodology papers of this form are accepted at systems and dependability workshops when the injection procedure is fully specified and reproducible.
P10  ·  Risk-Quantified Virtual Machine Right-Sizing for Private Cloud Capacity Reclamation
BACKGROUND
Virtual machines in private clouds are commonly provisioned according to the peak demand anticipated at the time of request. Since actual demand is usually far below that peak, a substantial fraction of allocated capacity remains idle. Right-sizing is the practice of reducing allocations to match observed utilisation.
PROBLEM STATEMENT
Right-sizing recommendations are conventionally reported in terms of the capacity they reclaim. This presentation is incomplete and potentially misleading, because reducing an allocation increases the probability that the workload will encounter resource exhaustion during a future demand spike. The risk introduced by a given reclamation is not quantified, so an operator cannot judge whether a recommendation is safe and has no principled way to select an operating point.
OBJECTIVES
O1.  To analyse utilisation telemetry from real production virtual machines and characterise the gap between allocated and used capacity.
O2.  To develop a right-sizing recommender that produces flavour recommendations from utilisation history.
O3.  To model, for each recommendation, the probability that the resized machine will exhaust its resources within a defined future window.
O4.  To present the outcome as a frontier relating reclaimed capacity to induced violation risk, allowing an operator to select an acceptable point.
SCOPE OF WORK
1.  Obtain the Bitbrains GWA-T-12 traces or the Azure virtual machine trace, both publicly available.
2.  Partition each trace into an observation period and an evaluation period.
3.  Generate recommendations from the observation period alone, without access to future data.
4.  Replay the evaluation period against the recommended allocations and record every instance of resource exhaustion.
5.  Repeat across several aggressiveness settings to trace the full frontier.
BASELINE FOR COMPARISON
Peak provisioning, which is current practice, and a simple 95th-percentile rule, which is the common heuristic recommendation.
EVALUATION METRICS
Reclaimed vCPU-hours and memory GB-hours; count and duration of resource-exhaustion events in the evaluation period; the frontier relating the two; the fraction of machines for which any recommendation is safe.
DATASETS AND TOOLS
Bitbrains GWA-T-12 traces, Azure public VM traces, Python with pandas and scikit-learn.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
The literature reports savings and is generally silent on the violations those savings caused. Producing the risk frontier, and stating plainly how much capacity can be reclaimed at zero induced risk, corrects a real reporting deficiency in this area.
P11  ·  Policy-Driven Cloud Bursting from Private to Public Capacity Under Cost, Latency and Data-Residency Constraints
BACKGROUND
Organisations that operate a private cloud size it for typical rather than peak demand and rely on public cloud capacity to absorb overflow. This practice, known as cloud bursting, requires a controller that decides when to burst, how much capacity to acquire and which work to send outward.
PROBLEM STATEMENT
Bursting controllers in practice trigger on a single utilisation or queue-length threshold. Such a controller cannot honour the constraints that actually govern the decision in an institutional setting: a monthly expenditure ceiling that must not be exceeded, a latency requirement that some public regions cannot satisfy, and a legal or policy requirement that certain categories of data remain within a jurisdiction. A controller that ignores these constraints will produce decisions that are operationally correct but administratively or legally unacceptable.
OBJECTIVES
O1.  To design a bursting controller that admits cost, latency and data-residency constraints as explicit inputs rather than as post-hoc filters.
O2.  To implement the controller against a private Kubernetes cluster with a public cloud node pool available for overflow.
O3.  To evaluate service-level attainment achieved per unit of expenditure under varying burst intensity.
O4.  To quantify the capacity and cost consequences of enforcing a data-residency constraint.
SCOPE OF WORK
1.  Deploy a local k3s cluster as the private capacity and configure a free-tier public cloud node that can join it.
2.  Label workloads with data-classification tags that determine which destinations are permissible.
3.  Implement the controller with a cost accumulator that halts bursting when the ceiling is reached.
4.  Drive the system with a load pattern containing bursts of varying magnitude and duration.
5.  Repeat the evaluation with the residency constraint enabled and disabled to isolate its effect.
BASELINE FOR COMPARISON
Threshold-only bursting without constraints, and a no-bursting configuration in which the private cluster absorbs or rejects all load.
EVALUATION METRICS
Service-level attainment; expenditure incurred; attainment per unit currency; requests rejected because no permissible destination existed; the attainment penalty attributable to the residency constraint.
DATASETS AND TOOLS
k3s, a public cloud free tier, Kubernetes custom controller in Go or Python, a load generator such as Locust.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Data residency is a live regulatory concern under the Digital Personal Data Protection Act 2023 and comparable regimes, yet it is almost never modelled as a first-class constraint in bursting research. Quantifying what compliance costs in attainment terms is both novel and directly relevant to Indian institutional deployments.
P12  ·  Carbon-Aware Scheduling of Deferrable Cloud Workloads Under Indian Grid Conditions
BACKGROUND
The carbon intensity of electricity, measured in grams of carbon dioxide equivalent per kilowatt-hour, varies through the day as the generation mix changes. Deferrable computational work, such as batch training, backups and analytics, can be shifted in time or between regions to coincide with lower-carbon periods. Scheduling algorithms exploiting this variation have been proposed and evaluated, overwhelmingly against European and North American grid data.
PROBLEM STATEMENT
The Indian grid has a markedly different diurnal carbon-intensity profile from the grids on which existing carbon-aware schedulers were evaluated, owing to high daytime solar generation combined with a substantial coal baseload and an evening peak served by fossil generation. An algorithm tuned to a grid whose cleanest period is overnight will behave incorrectly on a grid whose cleanest period is midday. Whether and by how much published carbon-aware scheduling algorithms underperform under Indian grid conditions is unknown.
OBJECTIVES
O1.  To assemble and characterise a carbon-intensity time series for one or more Indian regional grids and contrast its diurnal structure with a European reference grid.
O2.  To implement at least two published carbon-aware scheduling algorithms without modification.
O3.  To evaluate those algorithms against both grid profiles and quantify any degradation under Indian conditions.
O4.  To propose and evaluate an adaptation that accounts for the observed profile difference.
SCOPE OF WORK
1.  Obtain carbon-intensity data from the UK Carbon Intensity API and the ElectricityMaps free tier for the reference grid, and derive an Indian series from Grid-India or POSOCO generation-mix reports.
2.  Extend CloudSim with a carbon-accounting layer, or alternatively implement a Kubernetes scheduler plugin.
3.  Define a workload mixture containing both deferrable and latency-sensitive jobs with stated deadlines.
4.  Run each algorithm against each grid profile over an identical simulated period.
5.  Implement and evaluate the proposed adaptation.
BASELINE FOR COMPARISON
Carbon-agnostic first-come-first-served scheduling, a fixed overnight-shifting heuristic, and the unmodified published algorithms.
EVALUATION METRICS
Grams of carbon dioxide equivalent emitted; mean and 95th percentile job delay; deadline violations; the carbon saving forgone by applying an unadapted algorithm to the Indian profile.
DATASETS AND TOOLS
CloudSim or a Kubernetes scheduler plugin, UK Carbon Intensity API, ElectricityMaps free tier, Grid-India or POSOCO published generation data.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Demonstrating that a published algorithm transfers poorly to a differently structured grid, and diagnosing why, is a legitimate contribution that does not require inventing a new algorithm. It is also directly relevant to Indian data-centre operators and is likely to be well received at regional venues.
P13  ·  Reinforcement-Learning Autoscaling Evaluated Against Production Controllers Including Its Own Training Cost
BACKGROUND
Autoscaling adjusts the number of replicas serving an application in response to load. The Kubernetes Horizontal Pod Autoscaler reacts to a utilisation metric crossing a target, and KEDA extends this to event-source metrics such as queue depth. Both are reactive and can oscillate or respond too slowly to sharp load changes. Reinforcement learning has been proposed repeatedly as an alternative.
PROBLEM STATEMENT
Published reinforcement-learning autoscalers report improved service-level attainment against the Horizontal Pod Autoscaler, but they typically omit two costs that determine whether the approach is deployable: the compute and time required to train the agent, and the behaviour of the agent during the period before it has learned an adequate policy. An operator cannot evaluate the claimed benefit without these figures, and the omission is sufficiently widespread that reviewers routinely raise it.
OBJECTIVES

PROBLEM STATEMENT
These advantages are asserted widely in industry material and reproduced in academic work, but the supporting measurement is thin and rarely covers workloads of substance. Critically, the conditions under which WebAssembly performs worse than a container are almost never reported, although any runtime with restricted system-call access and a maturing compilation toolchain must have such conditions. A practitioner considering the technology therefore has access to its advantages but not to its limitations.
OBJECTIVES
O1.  To measure startup latency, memory footprint and sustained throughput for identical workloads under WebAssembly, container and microVM runtimes.
O2.  To identify workload classes in which WebAssembly performs worse than a container and to explain the cause.
O3.  To compare the isolation properties of the three runtimes qualitatively against a stated threat model.
O4.  To provide selection guidance stating explicitly when WebAssembly should not be chosen.
SCOPE OF WORK
1.  Select three workload classes: a short-lived request handler, a compute-intensive routine, and an input-output-intensive routine.
2.  Compile each workload for WebAssembly and package the identical logic as a container image.
3.  Execute under containerd, under WasmEdge or Wasmtime through runwasi, and under Firecracker.
4.  Measure the full startup latency distribution rather than the mean alone, since tail behaviour governs edge responsiveness.
5.  Document any workload that could not be compiled to WebAssembly, as such cases constitute findings in their own right.
BASELINE FOR COMPARISON
containerd, which is the established edge runtime and the incumbent that WebAssembly would have to displace.
EVALUATION METRICS
Startup latency distribution including tail percentiles; resident set size; sustained throughput; throughput degradation on input-output-intensive work specifically; count of workloads that could not be ported.
DATASETS AND TOOLS
containerd, WasmEdge or Wasmtime with runwasi, Firecracker, Rust or C compiled to the WASI target.
EXPECTED CONTRIBUTION AND PUBLICATION RATIONALE
Reporting the workload classes in which WebAssembly loses is what distinguishes a serious characterisation from promotional material, and it is the element reviewers will look for. The set of workloads that could not be ported at all is an additional and honest finding.
 
5.  Spare Statements
These are available if a team's environment proves unworkable, if an allocation clash arises, or for a repeat offering of the course. They are stated in outline; the full structure would be developed with the team on allocation.
S1  ·  Data-Residency Compliance Checking for Multi-Region Cloud Deployments
Context: The Digital Personal Data Protection Act 2023 and comparable regimes constrain where categories of personal data may be stored and processed. Cloud deployments described in Terraform or Kubernetes manifests specify regions, but nothing verifies those regions against the residency obligations attaching to the data the resources will hold.
Objective: To parse infrastructure declarations, associate resources with data classifications, and flag configurations that place regulated data outside permitted jurisdictions; evaluated against manually audited deployments for precision and recall.
S2  ·  Queue Latency and Fidelity Trade-off in Cloud-Hosted Quantum Circuit Execution
Context: Quantum processors are accessed as a shared cloud service in which submitted circuits wait in a queue, sometimes for hours. A classical simulator returns results immediately but cannot reproduce hardware noise.
Objective: To characterise, across a range of small circuits, the point at which the fidelity gained from real hardware justifies the queue delay incurred, using the IBM Quantum free tier and a local simulator as the two arms of the comparison.
S3  ·  Overhead Characterisation of Confidential Computing for Cloud Inference
Context: Confidential computing executes workloads inside a hardware-protected enclave so that the host operator cannot inspect memory contents. The protection is not free: memory encryption and enclave transitions add latency.
Objective: To measure the latency, throughput and memory cost of running inference inside an enclave relative to conventional execution, and to determine the model sizes at which the overhead becomes prohibitive.
S4  ·  Detecting Co-Location Interference from Guest-Visible Signals Alone
Context: A tenant in a public cloud shares physical hardware with tenants it cannot observe. Performance variation caused by a noisy neighbour is indistinguishable, from inside the guest, from variation caused by the tenant’s own workload.
Objective: To determine whether co-location interference can be detected using only signals available inside the guest, such as cache miss rates and timing variance, and to establish the detection accuracy achievable without hypervisor access.
