1. Literature Survey

Before designing our solution, we studied 13 papers published between 2021 and 2026 that deal with multi-cloud workload placement, network cost modelling, and cloud cost optimisation. The purpose of this survey was to understand what methods already exist, what datasets and testbeds researchers have used, and — most importantly — what gaps remain unsolved. The table below summarises each paper across five dimensions: the authors and venue, the method they used, the dataset or testbed they evaluated on, the primary metric they measured, and the specific limitation that is relevant to our work.

We classify each paper's limitation using three labels:

  • Gap: The paper does not address the egress-aware placement problem at all. Our work directly fills this gap.
  • Partial: The paper addresses some aspect (e.g., it models bandwidth or uses ILP) but misses critical elements such as live pricing, intra-region free tiers, or three-provider coverage.
  • Background: The paper provides foundational knowledge (pricing data, NP-hardness proof, egress stability study) that supports our methodology but does not attempt to solve the placement problem itself.

1.2 Summary of Gaps Identified

After reviewing all 13 papers, we identify three specific gaps that no single existing work addresses together:

  1. No live three-provider pricing integration: Most papers use either synthetic data, manual price collection, or cover only two providers. No paper queries all three major providers (AWS, GCP, Azure) via their public APIs in a single unified cost model at runtime.
  2. No topology-dependent egress modelling: Papers that do consider network cost use a flat per-GB rate regardless of provider. They do not model the fact that intra-provider traffic is free while cross-provider traffic costs $0.087–$0.12/GB depending on the sending provider. This distinction is critical because it means co-located components have zero egress cost.
  3. No parametrised cost-penalty quantification: No paper reports the cost penalty of ignoring egress as a function of traffic volume. They test one scenario and report one number. We will sweep traffic volumes from 200 to 1,000 GB/month and produce a curve showing how the penalty grows, making the result actionable for practitioners.

These three gaps together define the contribution of our work.

2. Problem Statement and Hypothesis

2.1 Background: How Cloud Pricing Works

To understand the problem, we first need to understand how cloud providers charge for two things: compute and data transfer.

Compute pricing is straightforward. Each provider publishes a price list for virtual machines (VMs). For example, a VM with 4 vCPUs and 16 GB RAM costs $121.47/month on AWS (t3.xlarge), $97.83/month on GCP (e2-standard-4), and $110.40/month on Azure (Standard_D4s_v3). These prices are publicly available and do not require an account to view. The natural instinct is to pick the cheapest VM for each workload — in this case, GCP.

Data transfer (egress) pricing is less obvious. When data leaves a cloud provider's network, the provider charges an egress fee per gigabyte. The rates differ by provider:

ProviderEgress RateIntra-Region TransferWhat This Means
AWS$0.09 per GBFree ($0.00/GB)Sending 100 GB out of AWS costs $9.00; sending 100 GB within AWS costs $0.00
GCP$0.12 per GBFree ($0.00/GB)Sending 100 GB out of GCP costs $12.00; sending 100 GB within GCP costs $0.00
Azure$0.087 per GBFree ($0.00/GB)Sending 100 GB out of Azure costs $8.70; sending 100 GB within Azure costs $0.00

The critical detail is the second column: transferring data between two services on the same provider in the same region is free. This means that if your web server and database are both on GCP, the data flowing between them costs nothing. But if your web server is on GCP and your database is on Azure, GCP charges $0.12 for every gigabyte sent from the web server to the database.

2.2 The Problem: A Worked Example

Consider a simple three-tier application: a web frontend, an application server (API), and a PostgreSQL database. The web tier sends 500 GB/month of user requests to the app tier, and the app tier sends 200 GB/month of queries to the database.

A cloud engineer using the standard approach would pick the cheapest provider for each tier independently:

  • Web tier: GCP is cheapest at $24.27/month (vs $30.37 on AWS, $35.04 on Azure)
  • App tier: GCP is cheapest at $97.83/month (vs $121.47 on AWS, $110.40 on Azure)
  • DB tier: Azure is cheapest at $157.44/month (vs $162.40 on GCP, $183.96 on AWS)

This gives a compute total of $24.27 + $97.83 + $157.44 = $279.54/month. Looks like the cheapest option, right?

But now consider the egress. The app tier (on GCP) sends 200 GB/month to the DB tier (on Azure). Since they are on different providers, GCP charges its egress rate: 200 × $0.12 = $24.00/month. The web tier and app tier are both on GCP, so that 500 GB transfer is free. The DB sends 10 GB to the internet, costing 10 × $0.087 = $0.87.

Total cost: $279.54 (compute) + $24.87 (egress) = $304.41/month.

Now compare this to putting all three tiers on GCP: compute would be $24.27 + $97.83 + $162.40 = $284.50/month. Egress would be only 10 GB to internet at GCP rates: 10 × $0.12 = $1.20. Total: $285.70/month.

The "smart" greedy approach is $18.71/month more expensive than the simple all-GCP approach. The engineer saved $4.96 on DB compute by choosing Azure, but paid $24.00 in egress for that decision — a net loss of $19.04/month. This is the problem we solve.

2.3 Problem Statement (Restated in Our Own Words)

Given a multi-component application where each component communicates with other components by sending a known volume of data per month, and given the published compute and egress pricing of AWS, GCP, and Azure, find the assignment of components to providers that minimises the total monthly cost. The total cost is the sum of (a) compute cost for each component on its assigned provider, and (b) egress cost for each pair of communicating components that are placed on different providers. Components placed on the same provider incur zero egress cost for their mutual communication.

The current practice — selecting the cheapest compute per component independently — fails to solve this problem because it treats each component's cost as independent. In reality, the cost of placing component A on provider X depends on where component B (which communicates with A) is placed. The costs are coupled, and the greedy approach ignores this coupling.

2.4 Falsifiable Hypotheses

H1 (Primary): An egress-aware Integer Linear Programme (ILP) reduces total monthly cloud cost (compute + network transfer) by at least 15% compared to the greedy cheapest-per-vCPU baseline, across representative multi-component application topologies with inter-component traffic volumes ranging from 200 to 1,000 GB/month, under published AWS, GCP, and Azure on-demand pricing.

How to read this hypothesis: "Method X" is the egress-aware ILP. "Metric M" is total monthly cost. "At least N%" is 15%. "Baseline B" is greedy cheapest-per-vCPU. "Condition C" is the traffic volume range 200–1,000 GB/month across three providers. If the ILP does not achieve 15% reduction in any of the tested topologies, the hypothesis is falsified.

H2 (Secondary): For applications where any single inter-component data flow exceeds 300 GB/month, placing those two communicating components on different providers will be more expensive than co-locating them on the cheaper single provider in at least 60% of tested topologies, even when the cross-provider compute saving exceeds $30/month.

What this means in plain English: If two components talk to each other a lot (>300 GB/month), keeping them on the same cloud is almost always cheaper than splitting them across clouds — even if the second cloud has a significantly cheaper VM. The egress cost outweighs the compute saving more often than not.

2.5 Research Objectives

  1. O1 — Build a unified cost model: Create a Python module that queries the AWS Price List API, GCP Cloud Billing Catalog API, and Azure Retail Prices API to fetch current compute and egress prices. All three APIs are publicly accessible and require no authentication or paid account. The module returns a structured pricing dictionary that the optimisation solver can use.
  2. O2 — Formulate placement as an ILP: Define binary decision variables xi,j (1 if component i is placed on provider j, 0 otherwise) and construct an objective function that sums compute cost plus egress cost. The egress term uses a product of binary variables to detect cross-provider placement and multiplies by the traffic volume and the sending provider's egress rate.
  3. O3 — Solve and compare: For small instances (3–5 components on 3 providers, giving 27–243 possible placements), solve the ILP exactly using the CBC solver via PuLP. For larger instances, implement a simulated annealing heuristic and measure its optimality gap (how far it is from the exact solution, in percentage terms).
  4. O4 — Quantify the greedy penalty: Run the greedy baseline and the ILP on at least five different application topologies (3-tier web app, microservice mesh, data pipeline, ML training pipeline, IoT gateway) at four traffic volume levels (200, 400, 700, 1,000 GB/month). Plot the result as a benefit-versus-traffic-volume curve showing how the ILP's advantage over greedy grows with traffic.

3. Testbed / Environment Evidence

3.1 Why a Simulation Testbed Is Appropriate

Our research question is: "Given published pricing data, which placement algorithm produces the lowest total cost?" This is a decision-algorithm question, not a performance-benchmarking question. We do not need to deploy actual VMs on AWS, GCP, or Azure because we are not measuring response time, throughput, or availability. We are measuring cost, and cost is determined by the pricing data (which is public) and the placement decision (which is what our algorithm produces).

This is analogous to how an airline uses a route-optimisation algorithm to find the cheapest set of flights without actually flying all possible routes. The fuel prices and distances are known inputs; the algorithm finds the best combination. Similarly, our compute and egress prices are known inputs; our ILP finds the best placement.

The P5 problem statement explicitly notes: "no paid cloud account is required since only pricing data is consulted."

4. Baseline Reproduced

4.1 Definition of Baselines

We define two baselines against which our ILP will be measured in Review 2:

Primary baseline — Greedy cheapest-per-vCPU: For each component independently, select the provider offering the lowest monthly compute price. Do not consider egress at all. This is the standard approach used in industry today — cloud cost calculators on AWS, GCP, and Azure websites all work this way, showing you the cheapest VM without factoring in data transfer to other components.

Secondary baseline — Single-provider placement: Place all components on a single provider (all-AWS, all-GCP, or all-Azure). This eliminates cross-provider egress entirely but may not give the cheapest compute prices. This baseline represents the alternative strategy of "just use one cloud and avoid complexity."

4.4 The Cost Inversion: $4.96 Saved, $24.00 Lost

This is the core finding of the baseline. Let us state it precisely:

Cost Inversion Analysis:

The greedy algorithm placed DB on Azure because Azure's DB instance ($157.44/month) is $4.96/month cheaper than GCP's ($162.40/month).

But this decision caused App(GCP) to send 200 GB/month across the provider boundary to DB(Azure), costing $24.00/month in egress.

Net result: Saved $4.96 in compute. Lost $24.00 in egress. Net loss: $19.04/month.

The egress cost is 4.84× larger than the compute saving. This is a cost inversion — the nominally cheaper option becomes the more expensive option when egress is included. The greedy algorithm, by construction, cannot detect this inversion because it does not model egress.

4.5 The Range of Possible Costs

Across all 27 placements, total monthly costs range from $285.70 (optimal, all-GCP) to $396.93 (worst, GCP+Azure+AWS). This is a spread of $111.23/month, or 38.9% of the optimal cost. The worst placement pays $78.30/month in egress alone — more than the entire compute cost of the web tier ($24.27–$35.04). This demonstrates that egress is not a minor line item; for cross-provider deployments with significant inter-component traffic, egress can become the dominant cost factor.

The top 8 placements are all either single-provider (ranks 1, 2, 8) or split only the DB tier (ranks 3–7). Placements that split the web or app tier across providers consistently rank in the bottom half because the 500 GB/month Web→App flow generates large egress charges ($45–$60/month) whenever these two components are on different providers.

4.6 Why the 6.1% Gap Will Grow to ≥15% in Review 2

The 6.1% gap observed here uses a conservative topology with moderate traffic volumes (200 GB/month for the largest cross-provider flow). Our hypothesis targets ≥15% across the full sweep. Three factors will increase the gap:

  1. Higher traffic volumes scale egress linearly but leave compute unchanged. If App→DB traffic increases from 200 to 1,000 GB/month (a realistic production volume for a SaaS application serving thousands of users), the egress cost jumps from $24.00 to $120.00/month. The compute saving ($4.96) remains the same. The cost inversion ratio goes from 4.8× to 24.2×.
  2. More components create more cross-provider edges. Our Review 1 topology has 3 components (27 placements). In Review 2, we will test a 5-component topology (adding a cache layer and a message queue), producing 35 = 243 placements. With 5 components, the greedy algorithm has more chances to split communicating pairs across providers, generating multiple simultaneous egress flows.
  3. Mesh topologies amplify the effect. In a microservice mesh where every service communicates with every other service, the number of potential cross-provider data flows grows quadratically with the number of services. The greedy algorithm, which evaluates each service independently, is systematically blind to this quadratic coupling.

5. Proposed Methodology (Review 2 Preview)

While the full implementation will be presented in Review 2, we outline the methodology here to demonstrate that we have a clear path from baseline to solution.

5.1 ILP Formulation Overview

We define the following decision variables and objective:

  • Decision variable: xi,j ∈ {0, 1} — equals 1 if component i is placed on provider j, 0 otherwise.
  • Constraint: Each component is placed on exactly one provider: Σj xi,j = 1 for each component i.
  • Objective: Minimise total cost = Σi,j (compute_costi,j × xi,j) + Σ(i,k) Σj≠l (traffici,k × egress_ratej × xi,j × xk,l)

The first sum captures compute cost. The second sum captures egress: for each pair of communicating components (i, k) placed on different providers (j ≠ l), multiply the traffic volume by the sender's egress rate. When both are on the same provider, the egress term is zero because xi,j × xk,l = 0 when j = l.

The product xi,j × xk,l makes this a quadratic integer programme. We linearise it using McCormick envelopes (standard technique) to convert it into a linear programme solvable by CBC.
