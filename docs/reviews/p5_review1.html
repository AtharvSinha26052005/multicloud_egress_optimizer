2 Problem Statement and Hypothesis

2.1 Background and Motivation

Organisations deploying multi-component applications across public cloud providers face a placement decision: assign each component (web tier, application server, database, etc.) to a provider and region. The dominant practice is to select the cheapest compute option per component independently. This approach ignores that data flowing between components on different providers incurs egress charges: AWS charges $0.09/GB, GCP $0.12/GB, Azure $0.087/GB for outbound traffic. For a three-tier application with 200 GB/month flowing from application server to database, a single cross-provider placement decision generates $24.00/month in egress — while the compute saving that motivated the split may be as small as $4.96/month. The compute saving is real; the egress cost is larger and invisible to the greedy algorithm.

The placement problem is therefore coupled: the cost-optimal placement of any component depends on where its communicating neighbours are placed. Independent per-component selection, which treats the costs as decoupled, systematically produces suboptimal solutions. The magnitude of the suboptimality is the empirical question our work answers.

2.2 Problem Statement (Restated in Our Own Words)

Given: (i) a directed application graph whose nodes are software components and whose edges carry known monthly data-transfer volumes, and (ii) the published compute and egress pricing of AWS, GCP, and Azure retrieved via their public APIs — find an assignment of components to providers that minimises total monthly cost (compute + egress), where egress cost between two components equals the sending provider's per-GB rate multiplied by the edge volume, and intra-provider egress within the same region is zero. The baseline to beat is the greedy cheapest-per-vCPU assignment, which ignores all egress terms.

2.3 Falsifiable Hypotheses

H1 — Primary Hypothesis
"An egress-aware Integer Linear Programme reduces total monthly cloud expenditure (compute + network transfer) by at least 15% compared to the greedy cheapest-per-vCPU baseline, across representative multi-component application topologies with inter-component traffic volumes of 200–1,000 GB/month, under published AWS, GCP, and Azure on-demand pricing."
H2 — Secondary Hypothesis
"For applications with any inter-component data flow exceeding 300 GB/month, cross-provider placement of the two communicating components will be more expensive than co-locating them on the single cheaper provider, in at least 60% of evaluated topology and traffic-volume combinations, even when the cross-provider compute saving exceeds $30/month."

2.4 Research Objectives

  • O1Build a unified cost model spanning compute and inter-provider egress for AWS, GCP, and Azure using the AWS Price List API, GCP Cloud Billing Catalog API, and Azure Retail Prices API — all public and free to query.
  • O2Formulate multi-component placement as an ILP in which the egress cost between each pair of communicating components is an explicit binary-weighted term in the objective function, ensuring the solver internalises cross-provider transfer costs.
  • O3Solve exactly for small instances (3–5 components, 3 providers, exhaustive or CBC solver) and implement a simulated-annealing heuristic for larger instances; report the optimality gap of the heuristic relative to the exact solution.
  • O4Measure the cost penalty of greedy placement relative to the ILP optimum across at least five application topologies and four traffic-volume settings; present results as a benefit-versus-traffic-volume curve, not as a single figure.

3 Testbed and Environment Evidence

3.1 Testbed Architecture

Our testbed is a Python optimisation environment. No live cloud deployment is required because the research question concerns the placement decision algorithm, not the runtime behaviour of deployed infrastructure. This is explicitly stated in the P5 scope: "no paid cloud account is required since only pricing data is consulted."

Software Environment: Python 3.11  ·  PuLP 2.7.0 with CBC 2.10 solver  ·  NumPy 1.26  ·  Requests 2.31
Pricing Data: AWS Price List API  ·  GCP Cloud Billing Catalog API  ·  Azure Retail Prices API
All three APIs are publicly accessible with no authentication or account required.
Baseline Script: baseline_p5.py — exhaustive evaluation of all 3N placements for N components.

3.5 Key Observation

Critical Finding Already Visible in Baseline: The greedy algorithm selects GCP for Web and App (cheapest compute) and Azure for DB (cheapest compute: $157.44 vs GCP $162.40, saving $4.96). This split causes App(GCP) to send 200 GB/month across the provider boundary to DB(Azure), incurring 200 × $0.12 = $24.00/month in egress. The compute saving is $4.96; the egress cost incurred is $24.00. This is a 4.8× negative return on the placement decision.

The worst placement (GCP→Azure→AWS) costs $396.93 vs optimal $285.70 — a 38.9% overspend due entirely to $78.30/month in avoidable cross-provider egress.

4.1 Baselines Named in the Problem Statement

Primary Baseline: Greedy cheapest-per-vCPU selection — selects the provider with lowest monthly compute cost for each component, independently, without modelling egress. This is current industry practice.
Secondary Baseline: Single-provider placement (all-AWS, all-GCP, all-Azure) — represents the alternative of avoiding multi-cloud entirely, with zero intra-provider egress between components.

The compute saving from placing DB on Azure vs GCP is $162.40 − $157.44 = $4.96/month. The egress cost generated by that decision is $24.00/month. The net effect of the greedy decision is a $19.04/month increase in total cost. The ILP, by internalising the egress term, correctly identifies GCP as the optimal DB placement despite it being $4.96 more expensive in compute.

4.4 Why the 6.1% Gap Will Grow to ≥15% for Review 2

The 6.1% gap demonstrated here uses conservative traffic volumes (200 GB/month App→DB). Our hypothesis targets ≥15% across the full topology sweep for three reasons:

  1. Higher traffic amplifies egress costs linearly but leaves compute costs unchanged. At 1,000 GB/month App→DB, the same placement decision generates $120/month in egress — a 6.3× larger penalty.
  2. Five-component topologies (adding cache layer + message queue) create more inter-component edges, increasing the probability that greedy creates multiple cross-provider flows simultaneously.
  3. The benefit-versus-traffic-volume curve (Objective O4) will show the crossover point at which the greedy gap exceeds 15%, directly validating or falsifying H1.
